### How a trade record moves a firm's posture — and why I stopped

**It does not, and the owner must rule.** The order says: *"If the honest answer is that the owner
must state how an NCR or a safety incident weighs against a stated rating, say so and stop on that
part."* That is the honest answer.

The band is *the rating the report states*, normalised on the owner's Run 107 ladder. To let a
trade record change it I would have to answer at least these, and **every answer is a threshold**:

1. How many nonconformances pull a **Satisfactory** firm to **Marginal**? Three? Five? Over what
   exposure — per firm, per work package, per thousand labour hours?
2. Does **one** stop-work order attributed to a firm take it to Red on its own, the way one takes
   the whole project's safety posture to Red?
3. Are the eight document types **equal**? Is a failed inspection worth the same as a late
   delivery on the procurement log?
4. Does a **closed** record still count? For how long?
5. What happens to a firm that has trade records and **no stated rating at all** — is it assessed
   or unassessed?

I invented none of these. **What I built instead is everything that needs no threshold:** the
column, the attribution, the per-firm grouping, the unattributed list, the unusable-row count,
and the statement on the reading that the records move nothing.

**The three rules in the order's own words are honoured, and trivially so, because no record moves
any posture at all:** never distribute an unattributed defect across firms; never assume the worst
firm owns it; never let an unattributed record change any firm's posture. An unattributable record
is **reported as unattributed**, in its own list, with its own count.

**Run 107's PM review hold is untouched.** An adverse posture is still held for a Project Manager
and asserts no band until a disposition is recorded.

### 5.2 Commissioning report and project completion (section 4.2) — A PROPOSAL, NOT A CHANGE

**I did not replace the cost test and I did not touch `compute.delivery_complete`.**

What it does today, verbatim in behaviour: `bac` positive, and `ev`, `pv` and `ac` each **exactly
equal** to it, and percent complete exactly 100. Any missing figure is False. It is applied
**ahead of** the required-core gate, deliberately, because completion is a fact about delivery
rather than a risk posture.

**What is wrong with it, stated plainly.** It is a **financial** test wearing the name of a
**physical** one. A project can spend its budget exactly and be unfinished; a project can finish
and come in under budget, and this test calls that project incomplete — the code's own comment
concedes it ("a project one pound short of budget is not Complete here"). Meanwhile the document
that actually closes a project out contributes a risk score and a date.

**What a commissioning report must state to close a project — my proposal:**

| Field | What it is |
|---|---|
| `commissioning_status` | the report's own word: Complete / Substantially Complete / Incomplete |
| `commissioning_completion_date` | the date it certifies |
| `commissioning_systems_total` | systems requiring commissioning |
| `commissioning_systems_accepted` | systems commissioned **and accepted** |
| `commissioning_outstanding_json` | the punch list — one row per outstanding item, with whether it blocks turnover |
| `commissioning_certifying_party` | who signed it |
| `commissioning_certificate_reference` | its identifier |

**And how it should relate to the cost test — the part the owner must rule on.** I see three
options and I am not choosing between them:

- **(a) Either.** Complete when the cost identity holds **or** the commissioning report certifies
  completion with no blocking outstanding item. Reaches the most real projects; weakest evidence.
- **(b) Both.** Complete only when both hold. Strongest; would make the owner's three authored
  all-figures-equal projects *stop* publishing Complete, which is a behaviour change he has not
  asked for.
- **(c) Replace.** The commissioning certificate becomes the test and the cost identity is retired.
  Cleanest conceptually; retires a rule the owner explicitly ordered in an earlier run.

**I recommend (a), and I have not implemented it.** It adds a path without removing one, and it is
the only one of the three that changes no existing project's status.

### 5.3 Contract value and the masked baseline (section 4.3) — **A FINDING, NOT A FIX**

The order asks whether reading the original as well is meaningful. **It is already read, and it is
already separate, and the module simply does not use it.**

- `WRITER_TIERS["bac"]` = `{change_order: 0, contract_value: 1, schedule_of_values: 2,
  pay_application: 3, monthly_report: 4}` — the change order **outranks the contract**.
- `WRITER_TIERS["baselineContractSum"]` = `{contract_value: 0, change_order: 1}` — the **original**
  is held separately, and the contract wins it. The comment there says so: *"the contract's own
  figure beats a change order's account of it."*

So the original baseline is not masked in the evidence store. It is masked **in A1.7 and A1.8**,
which read `bac` and never `baselineContractSum`.

**And the revised budget is correctly the only baseline for both of them.** TCPI asks what cost
efficiency the **remaining work** must achieve against the money that **remains authorised**;
Variance at Completion asks how the forecast compares with the budget the project is **actually
held to**. An approved change order changes both. Computing either against a superseded contract
sum would report a variance against money nobody is managing to — it would make every project with
an approved additive change look over budget on day one.

**What is genuinely missing is not a different baseline. It is the disclosure.** Run 116 measured
`bac = 4,050,000` sourced from `change_order` while the contract states `4,000,000`, and nothing
on the reading says so. A reader sees a VAC against a budget and is not told the budget was
re-based, by how much, or by which document.

**Recommendation, not implemented:** carry `baselineContractSum`, the `bac` in force, their
difference and the source document onto A1.7's and A1.8's readings as **disclosure**, with no
change to either arithmetic and no change to either band. I did not build it because the order
asked me to establish whether it was a finding or a fix, and it is a finding.

```
                   its absence is the whole point: a row stating a record and no firm is an
                   UNATTRIBUTED record. It is carried through, counted, and reported as
                   unattributed. It is NEVER distributed across firms, NEVER assigned to the
                   worst firm, and NEVER allowed to move any firm's posture.
record_kind        nonconformance, inspection failure, safety incident, permit violation, late
                   delivery, audit finding, commissioning defect -- the document's own word.
record_status      open / closed / accepted / rejected, as printed.
record_severity    the severity word the record prints, if any. NOTHING in this run ranks it,
                   bands it, or maps it to a colour.
record_date        the date the record carries.
```

Headings recognised, matched case-insensitively after trimming:

```
record_reference : record_reference, reference, record, record_id, ref, id, number, no,
                   ncr_number, ncr_no, item, item_id, finding, finding_id, po, po_number
subcontractor    : subcontractor, sub, firm, company, trade_contractor, trade, vendor,
                   supplier, responsible_firm, responsible_party, contractor, name
record_kind      : record_kind, kind, type, record_type, category, classification
record_status    : record_status, status, state, disposition, outcome, result
record_severity  : record_severity, severity, criticality, class, level
record_date      : record_date, date, raised, raised_on, issued, issued_on, reported
```

**What makes a row unusable:** it is not an object, or it states no `record_reference` under any
heading above. It is dropped, counted, and never repaired, defaulted or guessed at.

**The extraction prompt states both halves in terms:** name the firm the document names, and
*"where the record names no firm, return subcontractor as null … a guessed name would be
attributed to a firm it does not belong to."*
