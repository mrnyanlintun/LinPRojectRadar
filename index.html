    Handbook

    About the platform and how it works

    What Opus Gubernatio is and how it is built, plus the methods behind every signal and recommendation.

    What it is

    Opus Gubernatio takes the documents a project produces each reporting period, reads the reported figures from them, and runs an analytical layer over that evidence to produce a recommendation. The project manager records an independent assessment before the recommendation is disclosed, then records a decision after it, with the reasoning and the evidence relied upon. Every computed result is stored with the inputs and the code version that produced it, so what was shown at the moment of a decision can be reproduced rather than re-derived. The platform does not decide anything. It analyses evidence, presents what it found, and keeps the record of what a professional decided in response.

    The platform serves two audiences from one codebase: research participants, whose work can enter a de-identified research export, and operational users, whose work never does. Which notices, features, and export rules apply is governed by the account type, resolved server-side.

    The framework

    There is deliberately no named framework here. A name was considered more than once and set aside, because the contribution this platform supports is empirical evidence about how professionals respond to AI decision support, not a new governance framework. Naming the machinery would claim a kind of novelty the work does not need and does not assert.

    What occupies that place is a described capability rather than a named one. In one sentence:

    Opus Gubernatio analyses the documents a project produces each reporting period and presents a recommendation that a project manager records a decision against, keeping the evidence, the recommendation, and the judgment as one reproducible record.

    Method

    This section describes what the platform does. It makes no claim about what any study using it will find.

    1. 1. Evidence. A reporting period's documents are uploaded. The server reads the reported figures from each unique file once, caches the result by content hash, and stores what was read, so the same document always yields the same values.
    2. 2. Analysis. The analytical layer runs server-side over that evidence and stores every computed result with its inputs, code version, and the reporting period's data cutoff. The browser renders stored results; it does not recompute them.
    3. 3. Independent assessment. Before the recommendation is disclosed, the project manager commits a preliminary judgment. Once committed it is locked, and the recommendation stays hidden from every member of the project, including observers, until that lock is in place.
    4. 4. Recommendation. The stored recommendation is then disclosed, with the evidence behind it.
    5. 5. Decision. The project manager records a disposition against the recommendation, with a rationale field captured alongside it. One named person decides per project; observers read.

    Everything in the sequence is enforced server-side and recorded. The result is one reproducible record per decision: what the evidence was, what the platform recommended, what the professional judged before seeing it, and what they decided after.

    The analytical layer

    The analytical layer is 100 distinct computations, organised into four groups. Groups are described by what they are for.

    GroupPurpose
    Project HealthWhat condition the project is in
    Recommendation and GovernanceWhat should be done, and by whom
    Data and Evidence HealthHow trustworthy the evidence base is
    Portfolio LevelPatterns that need more than one project to exist

    The count of 100 excludes one value, the document risk score, which is recorded as a value the extraction model supplies rather than one the analytical server computes.

    Data and Evidence Health does not contribute to a project's status. Evidence quality describes what is known about a project, not the project's condition, and folding it in would make an early reporting period read worse for reasons that have nothing to do with the project. Portfolio Level computations require more than one project and never run on a single-project path. Statuses within a group are combined with Dempster-Shafer evidence combination, which surfaces disagreement between signals rather than averaging it away.

    Architecture

    The analytical layer is computed and stored server-side; the interface reads the stored results rather than recomputing them, so what a reviewer sees is exactly what was recorded.

    Frontend: served same-origin with the API

    Vanilla JavaScript, HTML5, CSS3. No framework. The interface renders stored results; it does not recompute them.

    Backend: single /exec endpoint

    A Python service that routes requests, holds API keys server-side, brokers persistence and AI, and computes the analytical layer. The browser never holds an API key.

    Persistence: relational database

    A relational store holds projects, documents, computed results, membership, and the decision record. Computed results are append-only: a recompute writes a new row and marks the previous one superseded, and once a submitted decision references a row, the database refuses to change it. Archived projects are retained and restorable.

    AI: document extraction only

    One AI call exists, and it runs server-side: reading the reported figures from uploaded documents, using claude-opus-4-6. The browser never holds an API key. Extraction runs once per unique file and is cached by content hash, so the same document always yields the same values.

    Nothing else on the platform calls a model. The analytical layer is deterministic arithmetic, the governance recommendation comes from explicit rules, and the guided assistant is scripted: it answers from a written knowledge library by keyword match and makes no model call at all. Where a capability is not implemented in this build, for example conversational AI, automated document audit, or speech, the server refuses it by name rather than failing quietly.

    Geocoding: Google, with a US Census fallback

    Project addresses are geocoded server-side through the Google Geocoding API, falling back to the United States Census geocoder when Google returns no result or cannot be reached. The address the geocoder matched is shown back on every surface that displays a location, because a pin on the wrong building looks exactly like a pin on the right one. A project that cannot be placed is saved without coordinates and stays in the project list, and a project whose address changed to one that could not be matched keeps its previous position, labelled as belonging to the previous address rather than shown as current.

    Access: username and password, or Google sign-in

    Accounts are issued by an administrator; there is no self-registration. Each project has one project manager who can decide, and observers who read. Membership is explicit, and adding or revoking it is recorded with who did it and when.

    Administration

    Administration

    Two tabs. People and access holds the accounts, who runs and who reads each project, and which scenario a person works through for the study. Monitoring and export holds where each participant has reached and the de-identified extract.

    Accounts

    Who runs and who reads a project

    Operational access. This decides who may open a project and act on it now. It is not the study.

    Create a project

    Creates the project and puts a participant on it as PM in one step. Research accounts cannot create their own, so this is where theirs come from.

    Project membership

    One PM decides for a project; any number of observers may read it. Revoking keeps the row, because membership history is itself audit evidence.

    Add a member

    What a participant works through for the study

    Study participation. This decides which scenario a person is taken through as research. It grants no access to any project and changing it does not change who may open one.

    Assign a participant to a scenario

    The assignment is what lets a participant record a period decision. Without one their project stops after the signals.

    Monitoring

    Where each participant has reached. This is progress, never performance. Nothing here says whether a decision was good.

    Before you begin

    A little about your background

    This is asked once, now, and never again. It records the professional background your later decisions will be read against.
