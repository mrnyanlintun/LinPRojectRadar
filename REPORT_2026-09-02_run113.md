## 3. What happens when a prompt exceeds a provider's context window

Measured by `server/tools/drive_run113_context.py` (new), which builds every prompt with the
**production builders** from the **real stored figures** of the census fixture project, uploaded
through the real upload route. Nothing is asserted from a report.

**(a) No context limit is declared anywhere.** The keys any provider block carries are
`base_url`, `path`, `key_env`, `wire`, `models`. `ProviderConfig` carries `role, provider, wire,
model, url, key_env`. The strings `context_window`, `max_input`, `131072`, `200000`,
`input_tokens`, `count_tokens` appear **nowhere** in `ai_provider.py`. The request bodies send
`model`, `max_tokens`, `messages` and optionally `temperature`. **`max_tokens` is the OUTPUT cap.
Nothing anywhere bounds the INPUT.**

**(b) Nothing silently truncates a prompt.** There is exactly one input cap on the whole path and
it is loud: `docx_text.DOCX_TEXT_LIMIT = 60000` characters *per .docx document*, which appends
`[DOCUMENT TRUNCATED: it is longer than this reader sends to the model.]` to the text the model
sees. (There is a second, `raw.decode(...)[:12000]`, on the .docx-that-is-not-a-ZIP fallback in
`extraction_client`.) Neither `spec_apply.build_prompt`, nor `recognition.build_prompt`, nor
either `_Client.complete` contains any slice of the prompt. **The silent truncation the order
feared does not exist.**

**(c) The prompts, measured.** Characters are the measurement; the token column is an estimate at
4 chars/token and is labelled as such — the platform ships no tokeniser.

| category | spec chars | PROMPT chars | est. tokens | fields carried |
|---|---|---|---|---|
| A1 | 28,451 | 30,606 | 7,651 | 6 |
| A2 | 18,834 | 27,640 | 6,910 | 6 |
| A3 | 20,288 | 23,426 | 5,856 | 8 |
| A4 | 30,380 | 33,165 | 8,291 | 18 |
| **A6** | **35,506** | **39,248** | **9,812** | 17 |
| B1 | 21,095 | 23,175 | 5,793 | 1 |
| B2 | 6,433 | 8,562 | 2,140 | 4 |
| B3 | 22,156 | 24,311 | 6,077 | 6 |
| B4 | 9,544 | 11,673 | 2,918 | 4 |
| C1 | 23,638 | 25,735 | 6,433 | 2 |

Second-pass categories also carry an upstream state report: at its largest (all six pass-one
categories computed) that is **944 characters**. **Worst case end to end: 40,192 characters ≈
10,000 tokens.** The largest extraction *text* prompt is 5,274 chars; the classify prompt 1,569.

**PREMISE IN THE ORDER PROVED FALSE.** The order cites Run 84's "roughly 60,000 tokens" for the
specification prompt. Against this fixture the largest is **≈ 9,800 estimated tokens** — about
one sixth of that. Run 84's figure is most plausibly a *character* count of an unscoped prompt,
predating its own `scope_signal_inputs` work. **The conclusion the order drew from it is still
correct and now rests on a measurement**: 10,000 tokens against Groq's 131,072 leaves roughly 13×
headroom. A prompt would have to grow by more than an order of magnitude before any window is
threatened.

**(d) What an over-length rejection actually surfaces as — measured, not argued.** A provider's
own 400 (`context_length_exceeded`) was constructed at the transport and fed to the real
boundary. It surfaces as:

```
ProviderCallError: groq (openai/gpt-oss-120b) returned 400: {"error": {"message":
"Request too large for model `openai/gpt-oss-120b`: tokens per request limited to 131072,
requested 190000", ...}}
```

It names the provider, names the model, and carries the provider's own reason verbatim (the first
400 characters of the body). `spec_apply.apply_category` turns that into category state `failed`
with the message as the reason, which is deliberately distinguished from `abstained` — a failure
must never be read as an evidence gap. **This is a loud refusal, not a truncation.**
Falsification: the same boundary, handed a normal 200, returns the answer, so the check can fail.

Two things the owner should know that follow from the same reading:

- **No pre-flight check exists.** The platform cannot tell him a prompt is too big *before*
  sending it; it learns from the provider's rejection. Given 13× headroom that is a reasonable
  place to be, but it is a fact about the code, not a design claim.
- **A `document` block cannot go to Groq or OpenAI at all**, at any size.
  `OpenAICompatClient.complete` raises `ProviderCannotCarry` naming the provider, and explicitly
  does *not* drop the document. So on a Groq deployment, **extraction from PDFs will refuse**
  rather than produce a reading from a prompt about nothing. That is correct behaviour and it is
  also a real constraint on switching extraction to Groq.

## 5. C1.5 — what the tree establishes, and the fix

**The order's goal 3 could be resolved from the tree, so it was, and I did not put the question to
the owner.** Two things in `models_cat89.py` decide it.

**PREMISE PROVED FALSE (Run 111's, quoted approvingly in the order).** Run 111 read the crash as
"the lookup sits on a line whose result its own route never uses". That is **half right, and the
half it misses is the deciding one.** `use` is consumed **twice**:

```python
use = MODULE_USE[module_id]          # line 928
ev  = _qualify(module_id, structure)
qual = _qualification_block(ev, use) # -> becomes row["qualification"]
if gated and not ev.eligible_for(use):   # C1.5 is gated=False — this half IS unused
```

`_qualification_block(ev, use)` becomes `row["qualification"]`, so `use` is **stored on the ledger
row** as `requested_use` and `eligible_for_use`. And `_qualify` performs the **same lookup
independently at line 137**, before the gate is ever reached — so deleting line 928 would not have
stopped the `KeyError` at all. Dropping the use would have meant inventing a null `requested_use`
for a row that the four Category-8 rows all fill: inventing an input, which rule 1 forbids.

**The tree already contained the answer, and nothing had claimed it.** `USE_REQUIREMENTS`
(`models_cat89.py:96-98`) declares:

```python
# Category 9 assesses evidence; it does not itself require qualified evidence, which would
# be the circular architecture section 22 forbids.
"quality_assessment": {},
```

Grepped across the whole tree: **`quality_assessment` was declared and referenced nowhere else.
No module named it.** The vocabulary was written for a Category-9 use, its comment describes
C1.5's situation exactly, and it sat unclaimed.

**The fix: `MODULE_USE["C1.5"] = "quality_assessment"`.** It requires *nothing* of its evidence —
an empty requirement set, not a relaxed one — and the route stays `gated=False`, so eligibility
still blocks nothing. What changes is that the module runs and its stored row names the use it was
assessed for.

**Measured, with a governed package record supplied:**

```

information_completeness : 0.5   (1 of 2 applicable required components present and usable)
qualification.requested_use   : "quality_assessment"
qualification.eligible_for_use: true
band_asserted : False   status_color : None   category_9_metadata_only : True
```

No band is invented; it stays metadata. With no structure it still abstains cleanly and
unchanged, which is why the census is unmoved. Nothing on the participant surface reads
`requested_use` (grepped: zero hits in any `.js`/`.html`/`.ts`), so no participant-facing surface
changed.

**Falsification:** a *local copy* of the four-entry pre-change table raises `KeyError('C1.5')` on

## 6. A defect found in a verification suite, and fixed

**`tools/test_run93_provider_switch.py` was making three live HTTPS POSTs to
`https://api.groq.com/openai/v1/chat/completions` on every run since Run 93** — while its first
printed line reads *"NO MODEL IS CALLED IN THIS FILE."*

Three call sites in sections 5 and 8 handed the **applier** to `Captured.install`, not the client:

```python
o_cap.install(sa.ProviderSpecApplier(ap.build_client(groq["spec"], environ=ENV_GROQ)))
```

`install` set `_request` on the applier, which has no such method and never calls one, leaving the
real transport underneath live. It went unnoticed because the checks pass either way: `provider`
and `model_id` are read off the applier *before* the call, and the resulting `ProviderCallError` is
caught by `apply_category` as state `failed`. **Three checks passing for the wrong reason.**

I found this by watching `urllib.request.urlopen`, not by reading the file — the agent proxy
reported three rejected CONNECTs to `api.groq.com` during the suite run and I traced them.

Fixed: the three sites install on the **client**, and `Captured.install` now raises `TypeError` if
handed anything without a `_request`, so the mistake cannot repeat silently. Re-run under a
urlopen spy: **zero outbound requests, 72/72 checks pass.** No key was ever present, so the
bearer token sent was the literal string `present-not-a-real-key`; no credential leaked.
