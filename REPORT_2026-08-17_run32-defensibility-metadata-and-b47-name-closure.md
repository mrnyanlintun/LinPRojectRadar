## 2. The discipline this task turned on

**The served defensibility object is the object under test, so it did not generate its own
expected values.** The expected inventory was rebuilt from the running instrument. Comparing the
object against another copied metadata table would have been the failure mode this repository
already knows by name: asserting against a copy of the logic.

That distinction is not academic here. `test_run11_defensibility_claims.py` re-runs the generator
and compares its output to the committed file byte for byte. It was green throughout. It could
not have been anything else: **the generator produces both sides of that comparison**, so when
the derivation is wrong the file matches it perfectly and the check still passes. The defect below
survived two runs behind a green guard for exactly that reason.

## 3. Root cause

The object is generated by `tools/build_run11_defensibility_evidence.py`. Two things were wrong
with the generator itself.

**Root cause 1: the generator read four of the six canonical structure maps.** It imported
`canonical`, `v3`, `v4` and `v5`. Run 31 added `canonical_v6` (Categories 8 and 9) and Run 32
added `canonical_v7` (Category 10), and neither run extended that list.

This is precisely the defect Run 30 fixed and wrote a comment about - "this scanned canonical.py
alone, so the eighteen Category-6 and -7 identities whose defining structures live in
canonical_v5.py were being described to a reader as 'not required by this module' on the very day
their production routes started requiring one". **The lesson was learned once and then not applied
twice.** The list is now built by globbing every `canonical_v*.py` on disk and asserting that each
one contributed a map, so there is no list left to forget to extend.

**Root cause 2: the execution statement was a binary and the instrument is not.** It emitted
either "disabled: concept only" or "implemented and computed by the server". The second sentence
was used for seven genuinely different situations at once.

## 6. The B4.7 name completion

The display name was already `Minimax Regret Decision Rule`. The **method-class identifier** was
not, and that was the part that mattered: the runner emits `Minimax_Regret_Decision_Rule`, and
**a lookup that stops matching does not fail - it silently returns nothing.**

Two consumers had quietly gone dead since the section-3 rename:

* `server/app/documents.py` - the recommendation basis, absent on every project;
* `assets/js/recommendation_options.js` - the courses-of-action frame, silently empty;
* `assets/js/module_charts.js` - the expected-regret chart, silently not drawn.

Four **test assertions had become vacuously true** for the same reason: they asserted the *absence*
of a `method_class` nothing emits any more, so they would have passed even if the module had
produced a row. All four now name both identifiers and test the property again.

Backward-compatible aliases are retained **only where stored rows are read**, since a period result
written before the rename still carries the old identifier. Nothing emits the alias.

**Current B4.7 mixed-name conflicts: 0.** Every surviving occurrence is the deliberate alias, a
historical audit record, the owner specification's own preserved wording, or the unreachable v19
runner in `models_gov.py` (overridden by `CAT10_CANONICAL`).
