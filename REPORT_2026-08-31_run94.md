## 3. The theme values, where they came from, and what is not defined

### The authority, and the order's premise about it

§5.4 asked whether the site supports more than one theme. **It does. The authority is
`server/app/theme.py`, and it names FOUR storable themes:**

```
THEMES = ("plain", "light", "newyork", "maria")
THEME_LABELS = {plain: Fairbanks, light: Miami, newyork: NYC, maria: Maria}
DEFAULT_THEME = "plain"   RESEARCH_THEME = "newyork"   (pinned, ignores stored preference)
```

`dark` (Gotham) is **archived** there — its own comment says it "still renders if forced, but it
is not a value a caller may store". **I tested all four storable themes AND the archived `dark`,
at both widths: ten renders per chart. None was skipped.**

### The values, read at runtime

Both charts now read the tokens with `getComputedStyle(document.body)` every frame/render. No hex
is hard-coded as a palette; the hexes that remain in the source are last-ditch fallbacks for a
script-order failure and are the values Run 90 already shipped.

Read back from the browser (`--flow-accent` is the token radar.css already names for this chart —
"Signal Flow doc→model lines"):

### Colours used that the theme does not define — stated plainly

**NO THEME TOKEN WAS ADDED. `assets/css/radar.css` IS UNMODIFIED.** Three things are not
straight token values, and here is exactly what they are:

1. **Sphere shading.** A lit planet, moon and the sun are drawn with a radial gradient running
   from the band colour **mixed 45% toward white** at the highlight, through **the exact band
   colour**, to the band colour **mixed 32% toward black** at the limb. The theme defines no
   "lighter green"; I computed it from the theme's own green. The body's dominant fill and its
   rim are the exact token, so a reader never learns a second colour language for a band.
2. **The field.** The depth wash runs from `--surface` (lightened 10% on dark grounds) to
   `--page-bg` (darkened 25% on dark grounds), with the horizon band at `--line` at 10–16%
   alpha. Both endpoints are tokens; the mix is mine.
3. **The failed-category cross** is `#ffffff`, taken through the theme's `--status-ink-red`.

## 5. Premises in the order that proved FALSE against the tree

1. **§5.4 / the briefing: "there are FIVE themes, not two."** There are **four** storable ones.
   `server/app/theme.py THEMES = ("plain","light","newyork","maria")`; `dark` is archived there
   by name and is not a value a caller may store. The briefing's CSS grep found five `body[data
   -theme]` blocks and read the archived one as live. I tested all five anyway.
2. **The briefing: "read the theme values at runtime because each theme redeclares them."**
   Mostly true, and the exception bit me. **`--heading` is redeclared only on `:root` and on
   `maria`.** The `newyork` and `dark` blocks override `--text` but not `--heading`, so on those
   two themes `--heading` resolves to the Fairbanks value `#0f1216` — near black. Measured, in
   the rendered canvas. That is a defect in `radar.css`; it is **not fixed here**, because fixing
   it moves a theme token and §6 does not put the stylesheet in scope.
3. **§3: "the leftmost column is Documents" implies documents are the widest column.** They are
   not: 27 documents against 42 modules. The briefing flagged this and it is confirmed — the
   module column sets the height and the doc column is spread across it.
4. **The briefing: "Run 90's Signal Flow drew 27 supported document types in its OUTER ring."**
   Correct, and preserved. Not false; recorded because I checked it.
5. Not false, verified: Three.js absent; `window.performanceCategories()` present and returning
   six; retired modules absent from `cat.modules`; the registry CSV at
   `p0-baseline/module_renumbering_map.csv`; `--flow-accent` declared in all five theme blocks
   with the comment the briefing quoted.
