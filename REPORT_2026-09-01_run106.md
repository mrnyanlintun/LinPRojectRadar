## 2. Indeterminate, and what Awaiting analysis now says

**The platform issues, stores, renders and describes "Indeterminate" nowhere.** Established by
measurement, not by the briefing's list.

- The word is gone from `compute.py`, `spec_projection.py`, `decision_brief.py`, `facade.py`,
  `documents.py`, `category_posture.py`, `app.js`, `decision.js`, `detail.js`, `neural_flow.js`,
  `projectnet2d.js`, `assistant.js`, `B1_signal_synthesis.md` and `C1_data_integrity.md`.
- Remaining occurrences are **historical narrative only** — "it was 'Indeterminate' until Run 106
  removed the word" — in the version-history block of `models.py`, and one line each in the JS
  files recording what was replaced. None is issued, stored or rendered.
- **`knowledge.js`, `simulations.js` and `VALIDATION.md` keep the word and are correct to.** Those
  are **B2.2 Rough Sets**: "Indeterminate" there is the rough-set boundary region — the upper
  approximation spanning several states — a domain concept with nothing to do with project
  status. The briefing listed `simulations.js` among the files to sweep; sweeping it would have
  destroyed a correct name. Reported rather than done.
- The status vocabulary is now **exactly** `{Complete, Green, Yellow, Amber, Red, Awaiting
  analysis}`, asserted as a set in `drive_run106.py`.

**The sentence.** `compute._awaiting_reason()` composes it; both status paths call the same
function, so they cannot word it differently. Measured, for a project with A3 unassessed:

> No project posture is issued this period, because a required category could not be assessed:
> **Cost Risk (A3) has not been assessed** — no module in this category was run for this period.
> The project status is withheld rather than imputed, and no value was substituted for what is
> missing.

It distinguishes *never called* from *called and produced no band*. It rides on
`project_status_basis.status_reason` and on the row as `project_status_reason`, and it is rendered
by `decision-ui.js renderPosture` and by the detail-page brief. **Fault proof:** a project with all
five categories assessed carries **no** such sentence, so it is about the withholding and is not
printed unconditionally.

**Rows already stored keep what they hold.** No migration, no rewrite.

**One client defect this would have caused, and it was fixed.** `normalizeStatusLabel` did not
know "Awaiting analysis", so `app.js statusKey()` would have slugged it to `awaiting-analysis`, a
key the legend's counts object does not hold — `counts[k]++` is `undefined++`, NaN, **no throw**,
and the project vanishes from the legend. That is Run 99's measured defect reproduced one word
along. `normalizeStatusLabel` now resolves it and `statusKey` maps it to the `empty` legend key.

## 3. Reasoning — B1.2, the missing category, and what was built

### B1.2 Weighted Voting

**Premise in the briefing, confirmed:** the weight profile already existed at
`models_gov.py:392` and matches the owner's exactly. **What the briefing did not say, and it
matters:** B1.2's *arithmetic* was **not** the owner's rule. It computed a **plurality of weight**
— which band *class* held most of the renormalised weight. That is a different quantity. On
`{A1 Green .28, A2 Green .28, A3 Red .17, A4 Red .11, A6 Red .16}` plurality says **Green**
(0.56 vs 0.44) and the owner's scored sum says **Amber** (+0.32). A module named Weighted Voting
that disagreed with the weighted vote setting the status is the Run 104 defect one level up.

**Ruling: the rule lives where the project rule lives, and B1.2 reports it.** New module
`server/app/simulation/project_posture.py` holds `project_posture()`, called by **both** status
paths and by B1.2. Reasons:

- A module row is **dispatch machinery**. It can be retired, disabled or fail qualification, and a
  status that existed only where a runner returned it would vanish with it.
- The **specification projection dispatches no modules at all**. A rule living in a runner would
  exist on one path and not the other — the exact class of divergence Runs 104 and 105 closed.
- B1.2 now publishes `status_color` = the project rule's band, plus `weighted_sum`,
  `category_scores` and `project_arithmetic`. It **cannot disagree** with the status it is named
  for. The plurality distribution survives as `class_votes` and decides nothing.

**No second copy of anything.** `BAND_SCORE` and `AVERAGE_CUTS` are **imported** from
`category_posture` (the owner's Run 104 scale and cuts, unchanged). The weight profile **moved**
into `project_posture` and `models_gov` imports it under the names it has always used —
`WEIGHTED_VOTING_CATEGORY_WEIGHTS` is now that import, not a duplicate.

**`COMPARISON_ONLY_MODULES` was renamed, not emptied.** It is now
`spec_projection.EXCLUDED_FROM_CATEGORY_ROLLUP = frozenset({"B1.2"})`. The old name had become a
false statement about the module it contains. B1.2 **stays excluded from the category rollup**,
for a structural reason unchanged since Run 87: its reading is a second-pass restatement computed
**from** the rollup, so admitting it would make B1's posture a restatement of the project status
and let a band re-enter the arithmetic that produced it. Renamed rather than aliased — two names
for one set is a drift hazard. Two suites re-pointed, with the reason recorded beside each.

### A category with no posture

**Renormalise. Never zero.** `project_posture` removes an unassessed category from the denominator
and renormalises the rest. Reasons, all pre-existing in the tree rather than invented here:

- `B1_signal_synthesis.md` shared rule 3: *"an abstaining signal casts no vote, **carries no
  weight**"*. Carrying no weight ≠ carrying weight toward zero.
- `canonical_v5.weighted_voting` already normalises "over the eligible independent signals
  actually voting".
- `models_gov.weighted_category_vote` has renormalised these same five since Run 89.
- **Zero would be a fabricated reading.** On a −2…+2 scale zero sits *between* Yellow (+1) and
  Amber (−1) and would read as a measured middling assessment when nothing was measured.

**An honest limit, stated rather than glossed.** The **required-core gate is unchanged and sits on
top**: unless all five carry a posture, no status is published. So on the *published* path
renormalisation is never reached with a category missing — the gate has already withheld. It
matters for `fused_band`, the band recorded **beside** a withheld status so that withholding cannot
conceal an adverse reading, and for B1.2's own reading. It is kept and documented rather than
replaced by a refusal the gate already performs.

**Fault proof for "never zero":** with only A1 and A2 assessed, scoring the other three as zero
gives +1.12 and bands **Yellow**; renormalising gives **Green**, which is what the platform
publishes. An absence is not a middling reading.

### Conservative Dominance

B1.1's arithmetic is untouched and its name remains accurate. Every description that said the
project takes the **worst** across the categories was corrected: `decision_brief._why` and
`_posture_rules`, `decision-ui.js renderPosture` (the card literally printed *"Worst band among the
categories that were assessed"*), `B1_signal_synthesis.md`, `C1_data_integrity.md`,
`category_posture.py`, `spec_projection.py`, `compute.py`.

## 4. The two new bands, proved on a real project

Both **OWNER-CALIBRATED**, `threshold_source = owner_configured_default`, owner strings stored as
`band_basis_id` — the Run 103/104 precedent. **`THRESHOLD_SOURCES` was not widened.** Reference
entries added to `band_reference_data.json` as `submittal_first_review_rejection_bands` and
`ncr_rate_bands`, the first carrying the owner's own words that the 30–40% figure is descriptive
and **not** the source.

### A4.3 Submittal Rejection Rate — measured **Amber**

`2 of 10 submittals receiving a first review were rejected (20.0%)`, from 11 assessed decisions in
all and 1 resubmission cycle.

- The band is on the **first-review** population. `canonical_v4.submittal_rejection` now returns
  `first_review_rate / first_review_rejected / first_review_assessed` beside the unchanged
  contract-4.3 `rejection_rate`. The first review is the **earliest decision** for a submittal, by
  decision day then revision id. **Fault proof:** the two quantities differ on the fixture
  (20.0% vs 18.2%), so banding the first-review one is a real choice.
- **The extracted-totals path does not band.** Bare totals carry no revision structure, so the
  first-review population cannot be identified and the owner's boundary is not attached to a
  different quantity. Measured: `status_color is None` with the reason stated.
- **Zero denominator → Not Assessed.** Measured on a register with no assessed decision.

### A4.4 NCR Rate — measured **Yellow**

`3 nonconformances against 100 inspections … That is 3.0 per cent of inspections performed in the
period.` `denominator_type='inspections'`, `reporting_period=1` stored on the row.

- **The ladder applies to two denominators only.** Measured: the same record with
  `exposure_unit='labour hours'` asserts **no band** and names the unit — 2/5/10 per cent means
  nothing over hours, and the ladder is not widened.
- **Override beats rate.** 1 NCR in 100 is 1% — Green by the ladder — but with an open critical
  NCR the module bands **Red**. **Fault proof:** the same rate *without* the override is Green, so
  the override moved it and a high inspection count did not dilute it.
- **Absent override fields are disclosed, never read as False.** A record stating none of the four
  carries `band_overrides_evaluated: false` and names all four as absent.

## 6. Goal five — the card names adverse evidence beneath a better status

**Established: an adverse reading could be hidden, in three ways.**

1. `decision_brief._finding` named adverse **categories** using `_SEVERITY = {red, amber}`. **Yellow
   does not rank**, so a Red module inside a category that averaged to Yellow appeared nowhere in
   the finding.
2. `_drivers` selects modules named in a category's `status_set_by`. Under **worst-wins (A6)** that
   is only the modules *at* the worst band — a Yellow module inside a Red A6 is dropped.
3. The card shows **four** drivers collapsed; the rest sit behind an expansion.

**Fixed.** `decision_brief._adverse_readings()` lists **every module reading that is not Green**, in
severity order, with no selection by category, by whether it set a posture, or by the project band.
It is published as its own `adverse_readings` block, rendered by `decision-ui.js renderAdverse`, and
named in the finding sentence by `_adverse_module_sentence`. The same is done in the detail page's
scripted brief (`detail.js`), which had the same three holes. **Not Green is adverse — no threshold
and no judgement.**

**Proved on the rendered DOM.** A second project, built through the real routes, publishing
**Green** with **A4.4 Red** inside it (A4.4 12 NCRs / 100 inspections = 12%, Red; A4 averages
{+2, +2, −2} = +0.667 → Yellow; sum 0.28(2)+0.28(2)+0.17(2)+0.11(1)+0.16(2) = **+1.89 → Green**).
The card's own `innerText`, read from Chromium with nothing supplied to a renderer:

> The project posture is Green, formed from all 5 required categories. **ADVERSE READINGS INSIDE
> THIS POSTURE, named regardless of the band above them: A4.4 Red** (12 nonconformances against 100
> inspections, a rate of 0.12 for each one. 10 are still open. That is 12.0 per cent of inspections
> performed in the period. Every Red override was evaluated against the record and none holds.) in
> A4 Document-Derived Condition Signals. The project status is a weighted vote over the five
> category postures and an adverse category moves the sum by its weight and no more, so a
> favourable project band does not mean these readings were absent, outweighed on their own terms,
> or found not to hold. Each is a finding at its own level.

The rendered card also contains no "Indeterminate", no "worst band among the categories", and does
state "weighted vote".
