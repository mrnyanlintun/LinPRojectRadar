**Two reconciliations are imperfect and are reported rather than papered over.**

1. **"Defer pending evidence" → `defer`.** The tree holds *two* candidates, `defer` and
   `request_evidence`, and they are not the same thing: one postpones, the other asks. The card's
   option states both at once. `defer` is stored because the recorded fact is that the decision
   was postponed. `request_evidence` is left in `DISPOSITIONS` unaltered for the research
   decision form, which offers the two separately. **Whether the card should offer them
   separately is not decided here.**
2. **"Override finding" → `reject`.** `reject` is the closest existing value and it is **not
   identical**: overriding a finding is substituting one's own judgment for it, which is not the
   same act as refusing it. **No new value was invented for this.** It is reported for a ruling.

**No authority is named or modelled.** `no_action_within_current_authority` is the participant's
statement about their own position. There is no authority table behind it and none is implied.

**No migration was needed.** `decisions.disposition` is `Text`, nullable, unconstrained. The
card's own decisions do not go to that column at all — they go to the append-only
`audit_events` table, whose `metadata` JSON column already exists.

### Rationale on accept — reported, not decided

**What the tree requires today:** the **client** disables **Record decision** until the rationale
is at least 20 characters, for **every** disposition including accept. The **server route**
(`projectdecisionrecord`) requires **no** rationale for any disposition, accept included. That is
the behaviour the card already had before this run and it is left exactly as it was.

**What would change if accept required one:** nothing on the client (it already enforces it);
the server route would need a per-disposition branch, which would be the first place in this
platform where one disposition is validated differently from another. **The owner has not ruled;
this run does not decide it.**

```
netstack div    .projnet2d-wrap    bg=rgb(255,255,255)  (radar.css:2073 `var(--surface, #0f1729)`)
```

**Findings.**
1. **`var()` in the SVG `fill` presentation attribute resolves.** The computed fills are real
   theme colours, not the hard-coded fallbacks.
2. **Both charts land on exactly the same colour — `rgb(255,255,255)`, the theme's own
   `--surface`.** They sit in the theme together, and they agree with each other.
3. **`:root` is not the level that decides.** `--surface` on `:root` is `#fbf3e3`; the theme
   class on `<body>` (`t-light` here) redefines it to `#ffffff`, and that is what every element
   in both chart stacks inherits. A reader checking `:root` alone would conclude the charts were
   painting the wrong colour; they are not.
4. **The one real oddity, reported and not "fixed":** the Signal Flow paints **two** full-frame
   rects, `--page-bg` and then `--surface` on top of it. The second is fully opaque and covers
   the first completely, so the `--page-bg` rect is dead paint. Removing it would change nothing
   visible, so it was left.

**I invented no colour and added no token.** If what the owner is seeing is that the chart is a
`--surface` slab sitting on a `--page-bg` page, that is the same relationship every other panel
on the site has — but it is a design question, not a defect, and it needs his ruling rather than
my guess.
