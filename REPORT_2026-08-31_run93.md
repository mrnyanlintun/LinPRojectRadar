## 1. How the owner switches provider

Set these on the Render web service under **Environment**. Render restarts the service on an
environment change, so **no redeploy and no code change is needed in either direction**. If you
change them any other way, restart the web service.

### To Groq

```
AI_PROVIDER=groq
GROQ_API_KEY=<your Groq key>
```

That is the whole switch. It moves **all three** call sites.

**If your Groq key is stored under a variable name that is not `GROQ_API_KEY`** — the order said
the key is named `Groq` and I could not read your environment to confirm the spelling — add one
more line naming it, and the platform reads that variable instead:

```
AI_PROVIDER=groq
AI_GROQ_KEY_ENV=Groq
Groq=<your Groq key>
```

Models default to `llama-3.3-70b-versatile` (extraction and specification application) and
`llama-3.1-8b-instant` (narration). **I did not verify those model names against Groq's live
catalogue — there is no key here and I could not call them.** If Groq rejects a name, set it
explicitly and nothing else changes:

```
AI_SPEC_MODEL=<the exact Groq model id>
AI_EXTRACTION_MODEL=<the exact Groq model id>
AI_NARRATION_MODEL=<the exact Groq model id>
```

### Back to Claude

Either delete `AI_PROVIDER` entirely, or set it explicitly:

```
AI_PROVIDER=anthropic
```

with `ANTHROPIC_API_KEY` set as it is today. **Deleting `AI_PROVIDER` is the safer of the two**:
with nothing configured the platform resolves anthropic and exactly the three model identifiers
that were literals in the source before this run. You can leave `GROQ_API_KEY` in place; it is
simply not read while `AI_PROVIDER` is anthropic.

### Two warnings you need before you switch

1. **PDF extraction will REFUSE under Groq, loudly.** Anthropic's Messages API takes a base64
   PDF as a `document` content block. Groq's OpenAI-shape chat-completions endpoint has no field
   that carries one. Rather than silently dropping the PDF and asking the model to answer about
   nothing, the Groq boundary raises `ProviderCannotCarry`, naming the provider and saying the
   document was not dropped. **`.docx` uploads are unaffected** — `docx_text` reads them locally
   into a text block, so they go through on any provider. This is a finding about Groq, not a
   defect, and nothing was shrunk or worked around to hide it. If you want extraction to stay on
   Claude while the analytical layer tests on Groq, that is one line:

   ```
   AI_PROVIDER=groq
   AI_EXTRACTION_PROVIDER=anthropic
   ```

2. **The specification prompt is roughly 60,000 tokens** after Run 84's scoping. I could not test
   whether Groq's context window and rate limits accept it. If it does not, that is a finding
   about Groq to report — the specification does not shrink to fit it.

## 3. Where provider and model are recorded, and how to query it

**Specification readings** — `specification_readings`, one row per press of a category:

```sql
SELECT category_key, period, state, status, served_by, provider, model_id, created_at
FROM specification_readings
WHERE project_id = '<uuid>' AND superseded_by IS NULL
ORDER BY period, category_key;
```

`served_by` is `model` or `recorded`; `provider` is the provider name (or the literal `recorded`
where a fixture served and no provider was asked); `model_id` is the model identifier. The API
carries all three: `reading_payload` returns `servedBy`, `provider`, `modelId`, and
`projectcategoryapply` echoes them on the response.

**Extractions** — `documents`, one row per unique file:

```sql
SELECT filename, doc_type, extraction_provider, extraction_model, extracted_at
FROM documents
WHERE extraction_model IS NOT NULL
ORDER BY extracted_at DESC;
```

Across a whole switch:

```sql
SELECT provider, model_id, COUNT(*) FROM specification_readings GROUP BY provider, model_id;
```

Rows written before this migration have NULL in both new columns. No value was invented for
them: the provider they were produced under was not recorded, and saying so is the honest record.

## 5. Should the extraction contract fingerprint include the provider?

**Conclusion: NO. It should not, and it was not changed.** The provider is recorded on the row
instead, by migration 0031.

The argument for including it is real and deserves stating fairly. The fingerprint exists because
a cached extraction can answer a contract that has since changed. A provider change arguably
changes what the extraction contract effectively is: the same prompt put to a different model is
not the same question, and after a switch to Groq the cache will serve you extractions that
Claude produced, without a model call, for every document already in the corpus.

Three things decide it against:

1. **It would silently rewrite the research stimulus.** The 0030 cache-miss path **updates the
   `documents` row in place**. Adding the provider to the key means switching to Groq re-extracts
   the entire corpus and overwrites what every stored row says the documents state — and
   switching back overwrites it again. Results already computed keep their own `signal_inputs`,
   but the corpus underneath them would have moved twice, mid-study, as a side effect of a
   setting change. That is a much larger act than the cache key was built for.
2. **The question it would answer is already answered, better.** The reason to want it is "which
   model produced this figure". `documents.extraction_provider` and `extraction_model` answer
   that per row, exactly, without touching anything. A cache key answers it only by destroying
   the older evidence.
3. **The fingerprint's own definition is the prompt.** `extraction_contract_fingerprint` is
   documented and implemented as the sha256 of the prompt `build_prompt` issues. The provider is
   who is asked, not what is asked. Folding the answerer into the identity of the question would
   make the column mean two things at once, and the 0030 docstring's rule — a contract change
   invalidates cached extractions "exactly once each" — would no longer hold, because a switch
   and a switch back would invalidate the same rows twice with no contract change at all.

**If you do want a provider-versus-provider extraction comparison**, the right way is a
deliberate, scoped re-extraction of chosen documents, not a cache key that fires on every switch.
That was not built; it was not in this run.
