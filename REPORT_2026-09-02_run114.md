## 2. THE THREE TABLE CONTRACTS, VERBATIM, FOR THE GENERATING MODEL

Each contract is **all-or-nothing**: one required cell missing and the structure is not written
at all, and the module abstains with its own sentence naming what it needs. Column headings are
matched **case- and separator-insensitively, and unit brackets are ignored** — `Total float
(days)`, `TOTAL FLOAT`, `total-float` and `total_float_days` are all the same column.

---

### 2.1 `weather_events_json` — on **`oac_minutes`** — serves **A4.5 Weather Day Impact**

**Field name:** `weather_events_json`
**Shape:** a JSON array, **one object per printed row** of the weather event table, keyed by the
minutes' own column headings.

**Every column below is REQUIRED. A row missing any one of them is dropped.**

| what it is | headings a parser recognises |
|---|---|
| the event's own identity | `Event ID`, `Event`, `Event No`, `Event Number`, `ID`, `Ref`, `Reference` |
| the date it happened | `Event Day`, `Event Date`, `Date`, `Weather Date` |
| the activity it stopped | `Activity ID`, `Activity`, `Activity No`, `Activity Code` |
| the schedule path that activity is on | `Schedule Path ID`, `Schedule Path`, `Path ID`, `Path`, `Network Path` |
| the days actually lost | `Actual Lost Days`, `Days Lost`, `Lost Days`, `Days Claimed`, `Days Impacted` |
| the float remaining on that path | `Available Float Days`, `Float Days`, `Total Float`, `Total Float Days`, `Float`, `Float Remaining` |
| what proves weather caused it | `Causal Evidence`, `Evidence`, `Cause`, `Basis`, `Verification`, `Substantiation` |

**Optional columns**, carried through where printed:
`Planned Work` / `Work Planned` / `Activity Description` / `Description` / `Work`;
`Mitigation Days` / `Recovery Days` / `Days Mitigated`;
`Event Start Date` / `Start Date` / `From` / `Period From`;
`Event End Date` / `End Date` / `To` / `Period To`.
The last two are only read when the record says it counts **calendar** days — they let the
delay be recounted in working days on the project's own calendar instead of being divided by a
working-day float.

**Scalars the minutes must also state, or nothing is assembled** (these are document fields,
not table columns):

* `weather_allowance_days_remaining` — the allowance the contract calendar **still has left**.
  Not the allowance granted.
* `weather_calendar_id` — the identifier or name of the weather calendar the minutes cite.

**Scalars that decide the band** (Run 107, already in the contract before this run):
`weather_days_claimed`, `weather_days_approved`, `weather_approval_period`,
`weather_allowance_days`, `weather_time_extension_granted`, `weather_time_extension_days`.
**New this run:** `weather_day_basis` (`approved_calendar_working_days` or `calendar_days`),
`weather_approval_source`, `weather_time_extension_incorporated_in_baseline`,
`weather_milestone_forecast_late`, `weather_milestone_class` (`contractual` or
`owner_committed`).

**WHAT MAKES A ROW OR A RECORD UNUSABLE**

* any one of the seven required columns absent → **that row is dropped**;
* no rows survive, or `weather_allowance_days_remaining` or `weather_calendar_id` absent →
  **nothing is assembled at all** and A4.5 abstains;
* a negative remaining allowance, a negative lost-day figure, or a negative float on any event
  → the whole record is refused;
* the days **claimed** are never read in place of the days **approved**. The owner's ruling
  stands: the module bands on what the owner approved in the minutes.

**A DIVERGENCE FROM THE ORDER, REPORTED RATHER THAN QUIETLY RESOLVED.** The order asks for
"the days claimed and the days approved" on each event row. The tree does not read them per
row: `canonical_v4._approved_weather_days` reads claimed and approved at the **record** level,
once, and nothing anywhere reads a per-event approved figure. Summing per-row claims into a
record-level approval would be inventing an approval. So the event row carries the days
**lost** and the record carries claimed and approved, which is where Run 107 already put them.

### 2.2 `procurement_items_json` — on **`procurement_log`** — serves **A4.9 Procurement Lead Time**

**Field name:** `procurement_items_json`
**Shape:** a JSON array, **one object per monitored item**, keyed by the register's own headings.

**Every column below is REQUIRED. A row missing any one of them is dropped.**

| what it is | headings a parser recognises |
|---|---|
| the item's own identity | `Item ID`, `Item`, `Item No`, `Item Number`, `ID`, `Tag`, `Package` |
| the date it is required on site | `Required On Site Day`, `Required On Site Date`, `Required On Site`, `Required Date`, `Need By`, `Need By Date`, `Required On Site By` |
| the date it is forecast to arrive | `Forecast Delivery Day`, `Forecast Delivery Date`, `Forecast Delivery`, `Forecast Date`, `Forecast On Site`, `Delivery Forecast` |
| the float on the activity it feeds | `Available Float Days`, `Float Days`, `Total Float`, `Total Float Days`, `Float` |
| whether it sits on controlling work | `Criticality`, `Critical`, `Criticality Class`, `Path Criticality`, `Schedule Criticality` |
| where it has got to | `Procurement Status`, `Status`, `State` |
| the activity it feeds | `Schedule Activity ID`, `Activity ID`, `Activity`, `Activity No`, `Feeds Activity` |

**Criticality is a word the register prints**, and one of: `controlling`, `critical`,
`critical_path`, `near_critical` (all read as controlling or near-critical) or `not_critical`,
`non_critical`, `noncritical` (read as the explicit negative). Anything else is **criticality
not stated**, and the Yellow/Amber split that needs it is not evaluated for that item. The
platform never reaches into Critical Path Analysis for it — no path exists from one module's
reading to another module's runner.

**Optional columns**, each carried only where printed:
`Forecast Uncertainty Days` / `Uncertainty Days`;
`Long Lead` / `Long Lead Item` / `Is Long Lead`;
`Protection Date Missed` / `Protection Date` / `Milestone Protection Date Missed`;
`Causes Required Milestone Late` / `Causes Milestone Late` / `Milestone Late`.
The last three carry the Red override and the Red arm of the ladder. **A column the register
does not print is NOT TESTED, never "did not hold".** Yes/no cells are read on the words a
register actually prints — `Yes`, `Y`, `true`, `1` are true; `No`, `N`, `false`, `0`, `-`,
`N/A` are false.

**Scalar beside it:** `procurement_day_basis` — `approved_calendar_working_days` or
`calendar_days`. Where it is absent or says calendar days with no project calendar available,
the day-count arms of the band are not evaluated and the module says so; nothing is converted
by a guess.

**WHAT MAKES A ROW OR A RECORD UNUSABLE**

* any of the seven required columns absent → **that row is dropped**;
* no rows survive → **nothing is assembled** and A4.9 abstains;
* negative float on any item → the whole register is refused;
* two items sharing one identity → refused (that is double counting, which the supplied
  contract names by name);
* a day basis this platform does not hold → refused.

The five existing scalars (`long_lead_items_total`, `on_schedule`, `at_risk`, `delayed`,
`report_date`) are **untouched and are not read by this structure**. A count ratio is not this
method.

### 2.3 `change_events_json` — on **`change_order`** — serves **A4.6 Change Order Frequency**

**Field name:** `change_events_json`
**Shape:** a JSON array, **one object per change event**, keyed by the register's own headings.
This is **not** `modifications_json`, which is B3.5's governance register (who executed each
modification and under what instrument). Both may be printed; they are different tables.

**Every column below is REQUIRED. A row missing any one of them is dropped.**

| what it is | headings a parser recognises |
|---|---|
| the change's own identity | `Change ID`, `Change`, `Change No`, `Change Order No`, `CO No`, `PCO No`, `ID`, `Ref`, `Reference` |
| the date it was issued | `Issue Day`, `Issue Date`, `Date`, `Issued`, `Date Issued` |
| what kind of change it is | `Change Type`, `Type`, `Category`, `Class` |
| why it arose | `Cause`, `Reason`, `Root Cause`, `Origin`, `Driver` |
| its value, unsigned | `Value`, `Amount`, `Change Value`, `Cost`, `CO Value` |
| whether it adds or takes away | `Direction`, `Sign`, `Add Or Omit`, `Addition Or Omission`, `Effect` |

**Direction is read from the word the register prints and is never decided from the sign of a
number.** Accepted as an **addition**: `ADDITIVE`, `ADD`, `ADDITION`, `INCREASE`. Accepted as
an **omission**: `DEDUCTIVE`, `DEDUCT`, `OMISSION`, `OMIT`, `CREDIT`, `DECREASE`. Anything
else and the row is dropped. An omission is never adverse and is reported as the reduction it
is; it is never added to the exposure the additions represent.

**Optional column:** `Reporting Period` / `Period` / `Report Period`.

**Scalars the document must also state, or nothing is assembled:**

* **`change_exposure_days`** — the span of time in **days** the register covers. This is the
  field Run 111 measured as having **no declared field anywhere in this contract**, and its
  absence is what made the whole recipe unsatisfiable. It is never computed from the dates of
  the changes.
* `baseline_contract_sum` — already on this document type; it is the baseline contract value
  the magnitude is measured against.

**Scalars for the schedule half of the band**, each stated or absent:
`change_related_delay_days`, `change_available_total_float_days`,
`original_contract_duration_days`, `change_time_extension_approved`,
`change_forecast_completion_moved`. **Float is never assumed to be zero** — assuming zero would
report a threatened completion on a project whose schedule was simply never measured. Where
delay or float is not stated the schedule half abstains and says so; the cost half still bands.

**WHAT MAKES A ROW OR A RECORD UNUSABLE**

* any of the six required columns absent, or a direction word the platform does not hold →
  **that row is dropped**;
* no rows survive, or `change_exposure_days` or `baseline_contract_sum` absent → **nothing is
  assembled** and A4.6 abstains;
* an exposure of zero or less, or a baseline contract value of zero or less → refused;
* a negative value beside a direction that already signs it → refused;
* two changes sharing one identity → refused.

### A1.8 Variance at Completion — the boundaries established, and the number I set

**What its boundaries were, measured at the parent commit:** Green at or above **0 per cent**,
Amber at or above **−11.11 per cent**, Red below. Three rungs, the same coarse shape.

**Why the Yellow edge is where I put it.** Because this forecast is the index-based one, the
VAC percentage is an **exact** restatement of the cost performance index —
`VAC% = (1 − 1/CPI) × 100`. That identity is already stated in the module and is what lets the
two existing edges be cited on the index at all: 0 per cent **is** an index of 1.00, and
−11.11 per cent **is** an index of 0.90. The owner set A1.7's Yellow edge at 1.05, which is the
planned efficiency moved by **half** the Christensen and Heise 0.10 stability margin. The same
construction on this module's own index, moved in this module's own adverse direction, is
`1.00 − 0.10/2 = 0.95`, and restating it by the identity gives:

> **Yellow edge = (1 − 1/0.95) × 100 = −5.263157894736842 per cent**

| | |
|---|---|
| Green | ≥ 0 per cent |
| **Yellow** | **< 0 and ≥ −5.263157894736842 per cent (index 0.95)** |
| Amber | < that and ≥ −11.111… per cent (index 0.90) |
| Red | below |

It falls strictly between the two existing edges, and **both of them are unmoved** — checked by
assertion, not by eye: `_TCPI_PLANNED_EFFICIENCY == 1.00`, `_TCPI_BEYOND_OBSERVED == 1.10`,
`_VAC_BUDGET_MET_PCT == 0.0`, `_VAC_BEYOND_OBSERVED_PCT == (1 − 1/0.90) × 100`. This inserts a
rung; it does not re-band. The planning briefing floated the CPI-0.95 analogue as a hypothesis
and asked me to test and justify it rather than take it as the answer. Tested: it is the only
construction that reproduces the owner's own arithmetic on this module's own quantity, and it
is exact rather than approximate because the identity is exact.

**Provenance, recorded accurately rather than inherited.** The number is the **owner's**. The
0.10 is Christensen and Heise's; halving it and placing a rung at the half is the owner's Run
114 ruling, made on A1.7 and carried across by the identity. No published source fixes 1.05 or
−5.26, and none is cited for either.

`band_boundary_provenance_class` is a **scalar** and cannot say two things. So it is left
describing the edges it always described — the definitional 1.00 / 0 per cent and the inferred
1.10 / −11.11 per cent, neither of which moves — and a per-edge record is published beside it:

```
A1.7   green_at_or_below   1.00   CODIFIED
       yellow_at_or_below  1.05   OWNER-CALIBRATED
       amber_at_or_below   1.10   CONVENTION
A1.8   green_at_or_above     0.00 per cent (CPI 1.00)   CODIFIED
       yellow_at_or_above   -5.263157894736842 per cent (CPI 0.95)   OWNER-CALIBRATED
       amber_at_or_above   -11.111… per cent (CPI 0.90)   CONVENTION
```

plus `band_boundary_provenance_classes = ["CODIFIED", "CONVENTION", "OWNER-CALIBRATED"]`, so
nothing reading a single field can miss that an owner-set edge is in the ladder. **This
placement of the scalar is a judgement and is flagged as one**, on the same footing as the Run
107 classification it sits beside: reported for a ruling, not presented as settled. If the
owner would rather the scalar itself read OWNER-CALIBRATED once any owner edge is present, that
is a one-line change.

`registry.BAND_SOURCES` for both modules now states the four-rung ladder and says in terms that
the Yellow edge is the owner's and is OWNER-CALIBRATED.
