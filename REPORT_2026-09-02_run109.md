## 4. THE CODE AND ASSEMBLY MODULES — WHAT IS BROKEN, AND WHERE

### A4.5 Weather Day Impact — ASSEMBLY (proved by measurement, not by grep)

Run 107 added six fields to the `oac_minutes` extraction contract
(`app/extraction_fields.py:337-346`): `weather_days_claimed`, `weather_days_approved`,
`weather_approval_period`, `weather_allowance_days`, `weather_time_extension_granted`,
`weather_time_extension_days`.

I uploaded an OAC minutes document stating all six through the real route and then read the
database. **They are extracted and they are in storage**, on the `documents.extraction` column,
verbatim:

```
oac_minutes {"document_date": "2026-03-31", …, "weather_days_claimed": 9,
 "weather_days_approved": 7, "weather_approval_period": "2026-03",
 "weather_allowance_days": 10, "weather_time_extension_granted": true,
 "weather_time_extension_days": 7}
```

`weatherImpactEvents` never appears in `signal_inputs`. The string `weatherImpactEvents` appears
in exactly one file in `server/app/**/*.py` — `app/simulation/canonical_v4.py`, where the module
declares what it reads. **No assembler exists.** `documents.py` contains no `elif doc_type ==
"oac_minutes"` branch in `_run69_structures`, and the six field names appear nowhere in
`documents.py`, `field_registry.py` or `extraction_merge.py`.

Two distinct breaks, both to be named by the fixing order:
1. **No join.** Nothing builds `weatherImpactEvents` from the stored extraction.
2. **No observation mapping.** The six fields are not declared in `app/field_registry.py`, so they
   produce no rows in the `observations` store either — `weatherDaysDiscussed` and
   `weatherDaysLost` do, the six new ones do not.

The module itself is sound: in M4 (`drive_run107.py`, `saveprojectdata`) A4.5 **bands Green** on
the same facts. Only the document-to-structure join is absent.

### A4.3 Submittal Rejection Rate — CODE (two defects in an assembler that does exist)

This is the one that looks like a document gap and is not. `documents.py:1916-1972` **does** build
`submittalDecisionRegister` from `submittal_decisions_json`. I supplied that table through the
real upload route and walked it forward one refusal at a time:

1. *Reviewer.* A row with no reviewer column is dropped (`documents.py:1936`). Correct and
   documented — the canonical function requires it. Not a defect; the register must print it.
2. *Legend.* A disposition the register does not map to one of `APPROVED`,
   `APPROVED_AS_NOTED`, `REVISE_AND_RESUBMIT`, `REJECTED`, `FOR_RECORD`, `WITHDRAWN`
   (`canonical_v4.py:398`) is refused. Also correct.
3. **DEFECT 1 — the decision date.** `documents.py:1924` reads the date column and
   `documents.py:1942` writes it straight into `decision_day`. `canonical_v4._day` (line 161)
   accepts **either** a numeric `decision_day` **or** a calendar `decision_date` — but it checks
   `decision_day` first, and a non-numeric value there **raises** instead of falling through to
   the date form. So a register printing `2026-02-05`, which is how every human-written register
   prints it, produces: *"…carries a day that is not a number, so no reading is taken from it."*
   Feeding an integer day instead makes the refusal go away — measured.
4. **DEFECT 2 — the reporting period.** `documents.py:1943` writes
   `"reporting_period": _r.get(...)` — a bare exact-key lookup, unlike **every other column on
   the same row**, which uses `_first_of(...)` heading matching. The extraction returns rows keyed
   by the table's own printed headings, so this is always `None`.
   `canonical_v4.submittal_rejection` (line 451) then filters `p["reporting_period"] == period`
   against the register's stated period and **no decision is ever in window**: *"No submittal in
   the register provided for this project was assessed in the period being reported."*

With both worked around in the fixture — an integer `decision_day` and a literal snake_case
`reporting_period` key inside each row — A4.3 **bands Amber** through the real upload route. The
module and the owner's ladder are fine; the join is wrong in two places, both in
`server/app/documents.py` lines 1916-1972.

Note also that A4.3's state *worsens* as the document set improves: on the thin corpus it is
"computed, no band" on the scalar path; supply the decision table and it becomes an abstention.

### C1.5 Information Completeness Ratio — CODE, and it is worse than an abstention

Two separate faults:

1. **No intake path.** `informationPackageRecord` appears only in `canonical_v6.py`. No extraction
   field, no assembler.
2. **A hard crash the moment the structure IS supplied.** I supplied a valid
   `informationPackageRecord` through the real `saveprojectdata` route and called the real
   `projectcomputeall`. It returned `{"ok": false, "error": "Server error: KeyError"}`. The
   traceback:

```
app/simulation/registry.py:765  run_all → record(new_id, run_module(...))
app/simulation/registry.py:603  run_module → fn(si, rand, period_cutoff)
app/simulation/models_cat89.py:928  use = MODULE_USE[module_id]
```

project. Any project that ever supplies this structure is bricked for computation. This defect is
latent today only because nothing supplies the structure. Removing `informationPackageRecord` from
the same fixture makes the identical run succeed — measured (M5 vs the A4.6-only variant).

## 5. THE DOCUMENT MODULES — THE FIELDS, NAMED

The owner is generating fifteen projects. These are what each document must state.

### A1.5 ARIMA CPI Forecast — eight reporting periods, not one field

`cpiHistory` is not asked of any document. `documents.py:1396-1411` builds it from **this
project's own strictly-earlier live computed rows** — one CPI per stored period — and
`models_evm.run_arima_forecast` (line 202) abstains below **eight readings**. So there is no field
to type in and no shortcut: the project needs **eight or more reporting periods**, each carrying
enough of a pay application / monthly report to yield `ev` and `ac`. Confirmed by measurement: on
the two-period fixture A1.5 abstains; on `drive_run107.py`'s ten-period fixture it **bands Green**.

The same mechanism, with a threshold of two rather than eight, governs **A1.2 CUSUM** — and A1.2
bands at period 2 in M3, so it is not blocked.

### A3.6 Cost Risk Analysis P80 — a risk register **as a table-bearing file**

`costRiskModel` is assembled at `documents.py:2724` from `register_exposure(_period_risks(...))`
plus the project's `bac`. The `ProjectRisk` rows it reads come from
`risk_rows_from_document(d.content, d.mime_type, d.filename)` — **the document's own stored
bytes**, parsed as a table. `documents.py:791` states the constraint outright: *"There is
deliberately NO model-returned fallback here… A register in a PDF yields no rows and says so."*

So the document must be a risk register **in a format whose tables parse** (a .docx or .xlsx
table, not a PDF), and its table must carry, per row: a **probability** and a **cost impact**,
alongside the description/category/owner columns. `bac` must also be present, which the contract
document already supplies.

**What I could not establish.** I did not exercise this end to end. Every document in the
measurement corpus is a placeholder PDF byte-string with no tables — the same corpus Runs 103 and
107 use — so `risk_rows_from_document` correctly returned nothing and `costRiskModel` was never
built. I am classifying A3.6 as DOCUMENT on a **code trace**, not on a measurement: the path from
an uploaded register to a banded reading exists and is complete in the source, but I have not seen
it run. If the fixing order wants certainty, the next run should upload one real .docx risk
register and observe.

**FALSE — Run 106's goal-four survey (eight modules needing thresholds) and Run 103's

**TRUE, and stronger than stated — the three canonical structure names.** `weatherImpactEvents`,

2. **Nothing here tests a real extraction model.** There is no `ANTHROPIC_API_KEY` and every

   correct by design or may be a second silent fallback; I did not trace it, and it is not counted
