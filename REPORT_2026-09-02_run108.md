## 3. THE CALENDAR

**Where it is extracted from.** The project's own **schedule update**, through the real extraction
contract. Two fields were added to `extraction_fields.SCHEDULE_UPDATE`:

* **`schedule_calendar_json`** — the calendar **definitions** the export prints.
* **`schedule_baseline_finish_date`** — the approved baseline finish as an ISO **date** (the
  pre-existing `schedule_baseline_finish_day` is a number on the schedule's own axis and cannot be
  counted against a calendar; it is **not** converted into a date).

**The shape the schedule document must state, verbatim** (`working_calendar.PROJECT_CALENDAR_CONTRACT`):

```json
[
  {
    "calendar_id": "the calendar's own name or id exactly as the export prints it",
    "working_days_of_week": ["monday","tuesday","wednesday","thursday","friday"],
    "holidays": ["2026-07-03","2026-09-07"]
  }
]
```

with the rules, verbatim:

* One object per calendar the export **defines**. Return every calendar it defines.
* `working_days_of_week` is the list of day names the calendar marks as working. It is read from
  the calendar definition the export prints and is **never inferred from the calendar's NAME**: a
  calendar called "5-day work week" states nothing about *which* five.
* `holidays` is the list of non-working exception dates the calendar defines, as ISO dates. An
  empty list means the export defines the calendar with no holidays. **Omit the key entirely** if
  the export prints no holiday table for that calendar.
* Return `null` for the whole field where the export defines no calendar. **Do not construct a
  calendar, do not assume a five-day week and do not assume a weekend.**

**How it is stored.** `documents.py` assembles `signal_inputs["projectCalendar"]` —
`{calendars, default_calendar_id, stated_calendar_names, assembled_by, source_document_type}` —
from the definitions only. A calendar reaches it **only** if it states at least one working day of
the week; a name reaches `stated_calendar_names` and is never read as a definition. The assembly
sits outside the `scheduleNetwork` guard, because a schedule update may define its calendars
without printing a readable activity network.

**The one conversion function.** `server/app/simulation/working_calendar.py`.

* `read_project_calendar(si, calendar_id=None)` — **the only door into a calendar in this
  platform**. Returns `None` where nothing is defined, where a named calendar does not match, or
  where two calendars are defined with no stated default (ambiguous: the first is never picked).
* **`working_days_between(cal, start_ordinal, end_ordinal)`** — the conversion. **Signed**; start
  exclusive, end inclusive; operates on `date.toordinal()` values, which is exactly what
  `canonical_v4._day` already produces from an ISO date, so a register printing dates needs no
  second parser.
* `working_days_in_span`, `period_spans`, `working_days_per_period` — built on the same primitive.

**All three arms call it.** A1.6 (`models_evm.py`), A4.9 and A4.5 (`models_doc.py`) each import
from this module and count nothing themselves. Proved discriminating: the same two dates give
**11** working days on the six-day calendar, **10** on the five-day one, and **12** with the
holidays removed.
