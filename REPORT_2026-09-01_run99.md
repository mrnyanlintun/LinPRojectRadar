## 1. Will every project publish the same thing regardless of its documents?

# YES — in this environment, and it is not close.

**Measured, through the real upload / `projectcomputeall` / `projectcategoryapply` routes, on
five separately built projects:**

| project | documents | earned/planned/actual | what the portfolio route served |
|---|---|---|---|
| A | 3, **not processed** | 25% under-run | *(no status — correctly awaiting analysis)* |
| B | 3, processed | 25%, CPI 0.952 | **Indeterminate** |
| C | 3, processed + categories applied | 25%, CPI 0.952 | **Indeterminate** |
| D | 3, processed + applied | **100%, EV=PV=AC=BAC** | **Indeterminate** *(before this run)* |
| E | **21 documents across 21 types**, processed + applied | on budget, on schedule, clean | **Indeterminate** |

Fixture E carried a contract, a time-phased baseline, a pay application, a schedule update, a
lookahead schedule, a resource report, a cost report, an RFI log, an RFA log, a submittal
register, an NCR log, a safety report, a quality audit, an environmental report, a subcontractor
report, a procurement log, an inspection report, a field report, a change order, OAC minutes and a
past-performance report. **Twenty-one documents produced exactly the same published status as
three.**

**Why.** The status the portfolio and the detail page serve comes from the **specification
layer**, not the Python module layer (`facade.live_statuses` → `spec_projection.projections`). In
a keyless environment that layer falls to `RecordedSpecApplier`, and the entire recorded corpus is
one hand-authored file, `research_fixtures/run76_recorded_a1_answer.json`, holding **one answer,
for A1 only**. Worse, the applier's lookup falls back to the bare category key
(`spec_apply.py:290`), so **A1 returns that same recorded answer whatever the figures are** —
fixture D at 100 per cent complete and fixture B at 25 per cent both received the identical A1
posture. Four of the five required categories return:

> *"no recorded answer is held for category A2 on these figures (prompt sha256 …), and there is no
> model key in this environment to ask. Nothing is invented in its place."*

The required-core gate then withholds the status and publishes `Indeterminate`.

**This is a fact about a keyless environment, not necessarily about the owner's deployment —
and I state the second half as reasoning, not measurement, because I cannot call a model.**
`spec_apply.build_applier` returns the configured provider's applier the moment its key is
present and never consults the recorded file at all. On a deployment with a working
`ANTHROPIC_API_KEY` (or `GROQ_API_KEY` per `AI_PROVIDER`), all ten categories would be put to the
model with the project's own figures in the prompt, the five required categories could all carry
postures, and the published status would then be the worst of them — **which means documents
would matter, and Green / Yellow / Amber / Red become reachable.** I could not verify that and I
do not claim it.

**What the owner should do before authoring fifteen projects:** confirm a model key is present in
the deployment he will generate them against, and generate **one** project first and check that
its portfolio row shows a band rather than `Indeterminate`. If it shows `Indeterminate`, the
remaining fourteen will too, whatever their documents say.

## 3. Why a "Computed" project showed "Awaiting analysis"

**The briefing's candidate line was wrong, and so was mine when I started.** `decision.js:245`
(`if (f && f.stored) return "Awaiting analysis"`) is *not* the line that fired: `getProjectFusion`
returned a **truthy** status (`"Indeterminate"`) for both projects, so that arm was never reached.

**The actual path, traced end to end and reproduced on the owner's own page:**

1. **What the compute route stored.** `simulation/compute.py` runs the 30 modules in service. On a
   three-document project only `A1.7`, `A1.8` and `B1.2` compute; **27 abstain** for want of
   document types with no contract. Only `A1` carries a posture, so the Run 89 / Run 95
   required-core gate publishes `project_status = "Indeterminate"`.
2. **What the portfolio route served.** `facade.live_statuses` publishes the *specification*
   layer's status (Run 79), which is `Indeterminate` for the same reason. That word reaches the
   browser verbatim as `p.status`.
3. **What the page read — the divergence point.** `app.js` `statusKey()` and `stateLabel()` asked
   `LinResults.hasResult(p)` **first**. At list-render time the results store has not primed, so
   that is false, and both fell through to `deriveHealthState()`'s *no stored row* arm, which
   returns `"Awaiting analysis"`. **The served word was never looked at.**
4. **A second, independent fault in the same function.** `renderStatusLegend`'s loop was
   `counts[statusKey(p)]++` inside a `try/catch`. `undefined++` is **NaN and does not throw**, so
   had the served word been read, the project would have vanished from the legend entirely
   without the catch ever firing. The loop could not fail.
5. **The green "Computed" dot is honest.** It comes from the membership meta
   (`workspaceprojects`), which reports that a computed row exists. It does. The label was the lie,
   not the dot. Section 3's branch (2) — "Computed is claiming something untrue" — is **false
   against the tree**.

**Fixed:** `statusKey()` and `stateLabel()` now read the served status **first**, on every row,
slim or full. `Awaiting analysis` is now returned only when the server published no status at all.
The legend loop counts an unrecognised key into `other`, never into `empty`, and exposes
`renderStatusLegend.lastCounts` so the totals can be reconciled against `LIN_PROJECTS.length`.

**Verified the owner's way**, at 1280px and 1024px: real server, real page, real routes, nothing
under test supplied to any renderer, `LinResults.rowFor` not substituted
(`server/tools/drive_run99.py`, **16/16**).

Before the fix — the owner's exact defect, reproduced:

```
legend: Complete 0 · Green 0 · Yellow 0 · Amber 0 · Red 0 · Awaiting analysis 4
B  DOM state='Awaiting analysis'  computed='Computed'
```

After:

```

A  DOM state='Awaiting analysis'  computed='Not yet computed'    <- uploaded, NOT processed
B  DOM state='Indeterminate'      computed='Computed'
```

## 4. Each of the six statuses

### Complete — WAS UNREACHABLE. BUILT THIS RUN. Project produced.

**Measured before:** a project seeded through the real routes with EV = PV = AC = BAC = 4,000,000
and 100 per cent complete published **`Indeterminate`**, identical to a project 25 per cent
through its work. `--status-complete` existed as a CSS token and `LEGEND_BANDS` named it, but a
token and a legend row are not a code path. The one promotion rule in the tree,
`deriveProjectStatus` (`assets/js/taxonomy.js:763`), is called only from `categories.js:444` and
`signals.js:856` — the **researcher deep-dive** surface, which recomputes in the browser. Nothing
on a participant's route calls it. `"Complete"` is not in `fusion.BAND_SEVERITY` and no server
module emits it.

**Built**, per §4.2, as one function in one place:

- `simulation/compute.py` — `_COMPLETE = "Complete"` and `delivery_complete(signal_inputs)`: true
  when BAC is a positive number, EV, PV and AC are **each exactly equal to it**, and the recorded
  percent complete is 100. **Exact equality, no tolerance** — the owner's condition is an equality
  and a tolerance would be a threshold this run invented.
- `spec_projection.py` **imports** that function rather than restating it, exactly as it already
  imports `_REQUIRED_CATEGORIES`, so the two status paths cannot drift.
- `facade.live_statuses` and `documents._result_view` pass the computed row's own
  `signal_inputs` (read-only; nothing stored is changed).

**Complete is decided AHEAD of the required-core gate.** The gate asks whether an official *risk
posture* may be issued; completion is not a posture but a fact about delivery, and no unassessed
category can make a finished project unfinished. Behind the gate, the owner's three complete
projects could never publish Complete — they carry the same unassessed categories as everything
else — and a status he ruled the platform publishes would be unreachable by construction.

**`"Complete"` is not added to `BAND_SEVERITY`**, never enters `worst_band`, and is never ranked
against a band. `fused_band` is still reported beside it.

**Project produced: fixture D**, through the real routes, reading `Complete` on the owner's own
portfolio page and counted `Complete 1` in his legend, at both widths.

### Green, Yellow, Amber, Red — reachable by the decision function; NO PROJECT PRODUCED, and I do not claim one.

**Nothing needed fixing for Yellow.**

### Indeterminate — the seventh word, and THE RULING THE OWNER MUST MAKE

**This is §4's escape clause taken deliberately, not a failure to decide.**

**The condition, named exactly:** *a project that has been processed, in which at least one of the
five required categories — A1 Cost and EVM, A2 Schedule, A3 Cost Risk, A4 Document Signals, A6
Delivery Quality — carries no posture.* Issued at `simulation/compute.py` (the required-core gate)
and, identically, at `spec_projection.project_status_basis`.

**How many projects land in it: ALL of them, today.** Every processed project in this environment,
with 3 documents or 21, except one authored to the Complete condition. **On his deployment, if the
model key is present, this should be none or few — but see §1.**

**None of the six fits it.** Not Complete. Not Green, Yellow, Amber or Red — asserting a severity
band from absent evidence is the one thing this platform is architected to refuse, and the fused
band is recorded beside the status precisely so it is not lost. **And explicitly not Awaiting
analysis, which by the owner's own definition means the opposite: that Process all has not been
pressed.**

**So I did not force a word onto it.** What I did instead: made every surface say the *same*
word — the server's own — instead of three different ones. **The owner must now rule:** either
`Indeterminate` becomes a seventh published status with a legend band of its own, or the
required-core gate stops withholding the fused band and the condition ceases to exist. **I did not
change the required core or Conservative Dominance** — §7 permits it only if it is why a legend
status cannot be reached, and this is a ruling, not a defect I may resolve.
