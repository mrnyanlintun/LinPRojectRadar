# Run 20 cycle 11: three numbers in the whole registry have a source

Every band boundary, cap, weight, membership and multiplier in this platform is a number
somebody chose. Run 4 cited the two voting modules' boundaries to published literature. Nothing
had ever done the same for the rest, so a boundary with a citation and a boundary invented in an
afternoon were indistinguishable from outside.

## What the sweep found

Eighty-nine modules carry a tunable value. Three carry published provenance and one carries a
mathematical constant. Everything else is UNSUPPORTED, and that is the finding of this cycle
rather than a failure of it.

The three are the two voting modules, whose boundaries rest on the Project Management Institute
definitions and on the cost performance index stability finding of Christensen and Heise, and
the isolation forest, whose tree count, subsample size and average path length normaliser are
the published defaults of the algorithm itself. That last one is the reason the register holds a
list of provenances per module rather than one class each: a published algorithm's own defaults
sit underneath an invented band ladder, and collapsing the module to a single class would have
hidden it. The Euler-Mascheroni constant inside the harmonic approximation is a mathematical
constant and not a choice.

No value anywhere in the registry is claimed as a regulatory value, because no provision cited
in this repository states one, and cycle 2 had already removed the assertions that said
otherwise. No value is claimed as an owner policy, because no owner policy document here fixes a
number.

## Nothing is calibrated and nothing pretends to be

Calibration needs an objective, a metric, an error-performance target, a calibration set, a
frozen selection, a holdout evaluation and a sensitivity analysis. The calibration set does not
exist: there is no labelled corpus of project outcomes in this repository and no expert
reference standard, and synthetic laboratory data is not empirical field validation. No entry
claims CALIBRATED_PARAMETER and the suite requires that none ever does without one.

## The multiplier that carried a percentile's name

The uplift multiplier in the two deterministic risk modules is 1.28, which is close to the
standard normal deviate at the ninetieth percentile and not at the eightieth, which is 0.8416.
Under the name those modules used to carry the number was wrong as well as unsourced. Cycle 10
removed the percentile claim from the name because nothing there is sampled and no distribution
is formed, so the multiplier no longer asserts a percentile of anything. As a multiplier it has
no source at all, and neither does the half applied to the index shortfall beside it.

## The two rows carried from cycle 9, revisited and reclassified rather than closed

The worst-count rule is defined by a fixed count out of a total, and the implementation triggers
on a fraction of the total, so every benign signal that arrives raises the count needed and can
switch an existing adverse set off. Cycle 11 searched the supervisory specification, this
repository and every source it cites and found no count in any of them. It is reclassified
PARAMETER_PROVENANCE_BLOCKED rather than closed with a fabricated constant.

The anomaly score's weights renormalise over whichever components are present, so the same
project scores differently according to data availability. Governing them means fixing them and
fixing them means choosing values no calibration evidence here can choose. It is reclassified
THRESHOLD_CALIBRATION_BLOCKED.

Both remain advisory and non-voting. THE RUN-20 EXIT TARGET OF IMPLEMENTATION_DEFECT EQUAL TO
ZERO IS THEREFORE NOT MET, and the reason is that meeting it required inventing two constants.

## The parameter its only caller never supplies, determined by execution

The forecast function accepts three trend inputs and genuinely widens its spread when they
arrive. Supplying all three to the production caller changes nothing in the published result;
supplying them to the underlying function does change it. The parameter is therefore DEAD ON THE
PRODUCTION PATH and the caller is incomplete. It is not scientifically required by the method as
implemented, it is not a default substituting for missing evidence, and no band, figure or
sentence this platform publishes depends on it. Whether the trend evidence should reach the
forecast is an owner method question and not a repair.

## Two vacuities found inside this cycle's own instrument

The sweep first subtracted a list of definitional values from the enumeration, and several of
those numbers are real band boundaries elsewhere: the line of balance bands at three days of
crew separation, and the change order module bands at three orders and five per cent of growth.
The subtraction removed them from view while the sweep reported itself complete. Nothing is
subtracted now and every module carrying any number at all must be classified.

The collector then took only module-level names bound directly to a constant. Both voting
modules derive one of their two boundaries from their source number by an expression, so the
only two sourced values in the whole registry were reported as absent while the sweep again
called itself complete. The collector now resolves expressions.

A third came from outside this cycle and is recorded with it: the Run 6 and Run 8 pinned
baseline guards enumerate production files through git, so a new production file that is not yet
tracked is invisible to them. The cycle 10 declaration guard caught it separately, so the
invariant was never actually unprotected, but a guard that only sees tracked files means less
than it appears to.
