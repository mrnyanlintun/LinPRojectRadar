## 3. PERT before and after, on the same network

The measure was rebuilt at **path** level. `canonical_v3.pert_criticality` now **records the
critical path in every trial** — a recording that did not exist at all before this run — and
`canonical_v3.path_criticality` counts **unique paths**, never a sum of activity indices.

On the corpus project's own 9-activity network, 2000 trials, through the real compute route:

| | Run 102/103 rule | Run 104 rule |
|---|---|---|
| quantity banded | criticality index of the **most critical activity** | **C1**, probability of the most frequently critical **path** |
| value | M900, share **1.00** | C1 = **1.00**, C2 = **0.00**, M = **1.00**, 1 distinct path |
| band | **Red** | **Green** |

The reversal is *measured*, not asserted: the driver re-applies the Run 102 cut table
(`pert_criticality_bands`, still in the reference file, now marked superseded) to the same stored
`most_critical_share` and gets Red, then reads the module's own new band and gets Green.

**Activity indices are not summed.** On this network they total **8.0**, which is why they cannot
be a path probability; the driver checks that explicitly.

**The reconstructed path is the real controlling path.** PERT's most critical path
`A100→A110→A120→A140→A150→A160→A180→M900` is byte-identical to the path A2.12 Critical Path
Analysis reports deterministically on the same network. One loop iteration was needed to get
there: the first implementation broke the early-finish tie by smallest id and dropped the
zero-duration completion milestone M900, giving a 7-activity path. Fixed by preferring an activity
with no successors.

**The dominance margin cap and the hard override, injected.** Harness. Two symmetric parallel
paths through the real `pert_criticality`: C1 = 0.507, C2 = 0.493, **M = 0.014** over 2 distinct
paths, which bands **Amber**, not Green. Then the cap table: a Green primary with M = 0.05 caps to
**Amber**; with M = 0.15 caps to **Yellow**; with M = 0.55 no cap. The hard override takes a
C1 = 0.99 reading to **Red** on negative float against the imposed finish, and **does not fire at
zero float** — the fault proof. *Declared weakness:* those cap/override injections re-apply the
cut table read from `band_reference_data.json` rather than calling the module; the module's own
applied values (`band_primary_before_cap`, `band_dominance_margin_cap`,
`band_hard_override_fired`) are separately read off the corpus reading.

**Threshold vocabulary was not widened.** `THRESHOLD_SOURCES` is untouched and remains exactly
`project_specific | formal_external_basis | owner_configured_default`. The owner's string
`owner_configured_PERT_path_concentration_tolerance` is stored as **`band_basis_id`**, exactly as
Run 103 established for `owner_configured_construction_control_tolerance`, with
`threshold_source = owner_configured_default` and `provenance = OWNER-CALIBRATED`.

**One deliberate behaviour change beyond the bands.** The hard override now fires on **negative**
controlling-path float, where Run 102's fired on **zero or negative**. The order says "negative
total float"; Run 102's own comment said zero float on a network with no imposed date is zero by
construction. The override remains **not evaluable** where the network imposes no finish, and says
so. Run 103's gating is kept: PERT still runs only after the network validates and only where
duration uncertainty is stated.

## 5. What the fusion and qualification path is still needed for

**Nothing was removed. This section is a report, as section 2.3 requires.**

`fuse_signals` is still called twice in `compute.py` and both calls still do work:

1. **The category call** no longer decides anything. Its band is stored beside the posture as
   `fusion_band`. What is still consumed from it: `conflict` (the decision brief prints "A
   disagreement between signals was computed in: A2 0.303, A3 0.2, A6 0.929"), `lineage_bodies`
   (the brief's "Bodies of evidence read" list), `within_lineage_disagreement`, and
   `excluded_non_evidential`.
2. **The project call `fuse_signals(voting)` still DECIDES the Python layer's `project_status`.**
   It is not a spare wheel. See 8.2.
3. `governed_status_semantics` reads the project conflict coefficient.
4. `dst_fuse` is a thin caller of `fuse_signals` and is used by Category 7 modules.

`qualification_gate` is **not** redundant either: `qualify()` is what REJECTS non-project evidence
(QUALITY_METADATA / GOVERNANCE_OUTPUT / DECISION_OUTPUT), which is the admission rule
`category_posture` inherits by being handed `to_fusion_signal()["status"]`; and `gate_reports` is
stored as `signal_qualification`.

**What would be safe to remove, if an order names it.** Only the *decision role* of the category
`fuse_signals` call — i.e. `fusion_band` — is now dead weight, and even that is deliberately
retained so a reader of a stored row can see what this run changed. **Nothing else is safe.**
Removing `fuse_signals` outright today would take the project status off the Python layer, empty
the brief's disagreement and evidence-body sections, and break Category 7. Removing the
qualification gate would remove the only module-level admission rule on that path.

**The lineage defect, confirmed exactly as Run 103 stated it.** `qualify()` ends
`QualifiedSignal(..., lineage or lineage_record(module_id))` — an empty record is manufactured for
a module declaring none, `to_fusion_signal()` passes it on, and `fuse_signals` therefore never sees
an *undeclared* signal and its documented safeguard never fires. **This run does not repair that;
it routes the decision around it.** The defect is still live for the two consumers above.
