## 5. Every contract grown, verbatim, for the owner's generating model

### `trade_denominators_json` — SIX NEW COLUMNS. One row per firm.

```
packages_due                firm work packages or milestones DUE in the reporting period.
                            The schedule reliability factor's denominator.
packages_completed_on_time  of those, the number COMPLETED ON OR BEFORE THEIR COMMITTED DATE.
                            The schedule reliability factor's numerator, and it is a COUNT THE
                            DOCUMENT STATES -- never derived from how many attribution rows
                            happened to arrive.
inspections_passed_first    firm inspections PASSED ON FIRST INSPECTION. The quality execution
                            factor's numerator, over the EXISTING inspections_performed
                            denominator. FIRST OUTCOME ONLY: a reinspection neither expands the
                            denominator nor counts again.
commitments_due             firm COMMITMENTS DUE in the reporting period. A commitment is the
                            owner's own list: a required submittal, an RFI response, a
                            procurement release or delivery, a corrective-action closure, or a
                            required change-document response.
commitments_met_on_time     of those, the number MET ON TIME. Stated, never derived.
active_work                 whether the firm had ACTIVE WORK in the reporting period.
```

**Headings a parser recognises, per column:**

```
packages_due               : packages_due, work_packages_due, packages, milestones_due,
                             activities_due, workfronts_due, planned_packages
packages_completed_on_time : packages_completed_on_time, packages_on_time, completed_on_time,
                             milestones_on_time, on_time_completions,
                             packages_completed_by_committed_date
inspections_passed_first   : inspections_passed_first, passed_first_inspection,
                             first_pass_inspections, inspections_passed, first_time_pass,
                             passed_on_first
commitments_due            : commitments_due, commitments, submittals_due, rfis_due,
                             responses_due, obligations_due
commitments_met_on_time    : commitments_met_on_time, commitments_on_time, commitments_met,
                             on_time_commitments, responses_on_time
active_work                : active_work, active, has_active_work, working_this_period,
                             on_site, mobilised, mobilized
```

**What makes a row unusable:** it names no firm. It cannot be attributed and is never spread
across firms. A column whose cell is blank or is not a number is skipped and the factor that
needs it is **UNAVAILABLE — never zero, never Green**. Counts for the same firm across several
documents are **SUMMED**; `active_work` is **NOT summed** — it is a statement about the firm in
the period, and the first document that states it wins, a later blank never erasing it.

## 6. What is shared with Run 118's engine, and the reasoning

The order's section 7.5 asks for an honest answer rather than a forced one. Here it is, item by
item.

**SHARED, and shared deliberately:**

* **The attribution and denominator READERS.** `documents.py` assembles
  `si["tradeAttributionRecords"]` once — records by firm, denominators by firm, unattributed
  rows, unusable counts. A6.4 reads that same assembled block. Nothing is rebuilt; the two
  engines read one table.
* **`fusion.BAND_SEVERITY`** — the {Green 0, Yellow 1, Amber 2, Red 3} ordering, imported by
  both, by `category_posture`, by `pm_review` and by `project_posture`.
* **The OSHA formula.** `trade_factors.OSHA_TRIR_CONSTANT` and `OSHA_TRIR_BASIS_ID` are
  imported, not copied. One codified formula, one constant, one basis identifier on this
  platform.
* **The safety override vocabulary.** `models_cat89._SAFETY_OVERRIDE_WORDS`, Run 101's closed
  set, imported and **not widened**. The owner's A6.4 sentence names the same condition Run 101
  built it for.
* **`pm_review.resolve`.** Run 107's hold and Run 119's lift extension. One hold, not a second.

**NOT SHARED, and not shared deliberately:**

* **The arithmetic.** Run 118 averages eight factors on a **+2/+1/−1/−2** scale. Run 120
  weights four factors on a **0/1/2/3 severity**. They share not one operation. Forcing one
  scale would mean a change to A4.8's calibration silently changing A6.4's, and the order
  explicitly permits two honestly separate scales.
* **The override vocabularies, except safety.** Run 118's `_NCR_OVERRIDE` was written from a
  DIFFERENT owner sentence, in a different order, for a different module. The two overlap
  heavily and are not the same set. Binding them would mean that amending one owner sentence
  silently amends the other module's override. A6.4's `_QUALITY_OVERRIDE` is written from the
  A6.4 sentence and the overlap is recorded in the code.
* **The denominator philosophy differs, and that difference is load-bearing.** Run 118 refuses
  to admit a firm that has only a denominator row, because a firm with a population and no
  records is clean on all eight of its factors — a manufactured Green. Run 120 admits it safely,
  because every one of its factors has a STATED NUMERATOR too, so a bare population yields four
  unavailable factors, fails eligibility, and reaches the fallback or Not Assessed. That is why
  a shared engine would have been wrong even if the scales had matched.
