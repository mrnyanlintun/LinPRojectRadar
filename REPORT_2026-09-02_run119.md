## 4. Every contract grown, printed verbatim for the owner's generating model

### 4.1 Goal 3 — the dispute record. **It needed ONE new fact and it was already extracted.**

The briefing's premise was right and I confirmed it: `documents.py` already parses
`dispute_id`, `subject`, `parties`, `raised_day` (from `raised_day`, `raised_date`,
`date_raised`, `date`, `raised`), `status` (from `status`, `state`, `position`) and
`recorded_in` out of `disputes_json`. So the raised date and the status column both existed.

What duration additionally needed:

1. **An as-of day to measure against.** Supplied by the OAC minutes' own `document_date`, which
   is already in the extraction contract for `oac_minutes`. **No new extraction field was
   asked for.** The system clock is never read.
2. **How "resolved" is read off `status`.** A closed vocabulary, printed verbatim:

```
DISPUTE_STATUS_RESOLVED = {"resolved", "closed", "settled", "withdrawn"}
DISPUTE_STATUS_OPEN     = {"open", "outstanding", "unresolved"}
anything else  -> not read as open and not read as resolved; the dispute is reported
                  unreadable and enters no band
```

That last rule is the `compliance_register` precedent applied unchanged — "a row printing
neither is outstanding and enters no ratio".

3. **The project's working calendar**, which already exists (Run 108, `schedule_calendar_json`
   on `schedule_update`). No growth.

**The contract as printed in the code** (`canonical_v4.DISPUTE_DURATION_CONTRACT`):

```
structure_key         : disputeRecord
required_on_record    : source, disputes, as_of_day
required_per_dispute  : dispute_id, raised_day, status
optional_per_dispute  : subject, parties, recorded_in
as_of_day             : the date the record speaks as of -- the meeting minutes' own document
                        date. A duration is measured from the day a dispute was raised TO a
                        stated day, and the system clock is never that day.
calendar              : the project's own approved working calendar, from the schedule update's
                        `schedule_calendar_json`. There is no default calendar and calendar days
                        are never substituted for working days.
```

### 4.2 Goal 5 — the commissioning report. **Two fields, not Run 117's seven.**

```
"commissioning_items_total":
   "The total number of items, systems or assemblies the commissioning report covers, as the
    report itself states it. A whole number above nought. Return null where the report states
    no total -- do not count rows to make one."

"commissioning_items_cleared":
   "How many of those items the report states are CLEARED FOR TESTING. A whole number at or
    above nought and not above the total. Return null where the report does not state it. Do
    not read 'complete', 'accepted' or 'turned over' as cleared unless the report itself uses
    those words for clearance for testing."
```

Why two and not seven: the question the owner asked is "is every item cleared for testing", and
these two answer it. Status, completion date, certifying party, certificate reference and the
punch list's blocking flag are provenance and narrative, not the test; `document_date` already
dates the reading. The outstanding count is **derived** (total minus cleared) rather than
extracted, so two figures can never disagree with a third.

### 4.3 Goal 2 — two document types gain the two denominators the ladder is already drawn over

`quality_audit_report` and `field_report` each gain `inspections_performed` and
`active_work_packages` — **the NCR log's own field names, reused, not respelled**, so the pooled
denominator cannot come to mean two things. No new numerator field was needed:
`quality_audit_report` already states `total_findings` and `field_report` already states
`quality_deficiencies_noted`.

All new fields are declared in `information_completeness._ASSEMBLER_FIELDS` — the two
denominators on both types, and each type's own numerator (`total_findings`,
`quality_deficiencies_noted`), because the pooled rate really does read all of them. The pinned
denominator moves **187 → 193** (candidate A 297 → 303) and `drive_run115`'s three pins were
moved with it, with the reason recorded in the file.

### 5.3 What stopped it — QUESTION ONE, and it is not the one the order anticipated

**A6.4 averaging A6.1, A6.2 and A6.3 double-counts them into its own category, and A6 is
worst-wins.** A6.4 sits in A6 Delivery Quality Performance, which forms its posture by
worst-wins over A6.1, A6.2, A6.3 and A6.4. If A6.4 becomes an average that *includes* A6.1,
A6.2 and A6.3, those three readings enter A6 twice — once directly and once through A6.4. Worse,
A6.4 would import A2 schedule and A3 cost adversity into the **Delivery Quality** category, and
A2 and A3 already vote in the project's weighted rule in their own right. A project with an
Amber critical path would then push A6 Amber through A6.4 and vote Amber twice.

The platform has an existing answer to exactly this shape and it is instructive: **B1.2 Weighted
Voting is a second-pass module that reads the category rollup, and it is in
`EXCLUDED_FROM_CATEGORY_ROLLUP` precisely so that it cannot feed the rollup it read.** The
mechanism for a module that reads other modules exists (`compute.compute_project` computes B1.2
after the rollup). What does not exist is a ruling on which of these two the owner wants:

* **(a)** A6.4 is excluded from the A6 category rollup, as B1.2 is — which changes what A6 means
  and removes contractor performance from Delivery Quality, a category the owner's own Run 104
  reasoning describes as covering contractor performance; or
* **(b)** A6.4 stays in A6 and the three A6 modules and the A2/A3/A4 modules are counted twice.

**Neither is mine to choose.** Both change how the project status is formed on every project.

### 5.4 What stopped it — QUESTION TWO: the stated rating

The order permits stopping here if the tree does not settle it. **The tree does settle it, and I
report the answer rather than the stop**: Run 118's A4.8 is explicit in production code — "THE
STATED RATING IS THE STARTING BAND; THE FACTORS ADJUST IT" — and this run's Goal 1 ruling
reinforces it, because holding a two-band lift only makes sense if the stated rating is
substantive rather than one vote among many. So the contractor's stated rating from the past
performance report should **set a starting band that the sixteen modules adjust**, on the A4.8
precedent, with a two-or-more-band lift held for PM review by the hold Goal 1 just built.

That is my reasoning and I would have built it that way. It is question one that stopped the
goal, not this one.

### 5.5 What is therefore true today

A6.4 still reads the past performance report alone and still bands Amber on the census fixture
from a stated score of 76 out of 100. Nothing about it changed this run.
